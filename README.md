# Джарвис

Агрегатор инвестиционного портфеля: FastAPI-бэкенд + React-фронтенд + PostgreSQL,
с фоновым планировщиком, который сам обновляет котировки, синхронизирует счета
Т-Банка и снимает ежедневный снимок стоимости портфеля — без ручных действий
владельца.

Куда движется проект — [`docs/roadmap.md`](docs/roadmap.md). Описание системы
целиком — [`docs/superpowers/specs/2026-08-07-jarvis-investment-design.md`](docs/superpowers/specs/2026-08-07-jarvis-investment-design.md).

## Требования

- Docker с `docker compose` (Docker Desktop или аналог, например Rancher Desktop) —
  для запуска всего стека одной командой.
- Python 3.12+ с [`uv`](https://docs.astral.sh/uv/) — для запуска бэкенда вне контейнера
  и тестов.
- Node 22.13+ с `pnpm` 11 (через `corepack enable`) — для разработки фронтенда
  вне контейнера. Пакет `pnpm@11` требует именно эту версию Node; более старой
  `node:20-alpine`, как можно было бы ожидать, для сборки фронтенда недостаточно —
  поэтому `frontend/Dockerfile` тоже собирается на `node:24-alpine`.

## Токен T-Invest API

Бэкенд ходит в T-Invest API Т-Банка от имени владельца портфеля, поэтому нужен
персональный токен:

1. В приложении/личном кабинете Т-Банка выпустить токен T-Invest API **с правами
   только на чтение** (без права на торговые операции и вывод средств). Джарвис
   только читает операции, портфель и справочник инструментов — торговый доступ
   ему не нужен и не должен выдаваться.
2. Скопировать `.env.example` в `.env` и вписать токен:

   ```bash
   cp .env.example .env
   ```

   ```
   TBANK_TOKEN=<токен с правами только на чтение>
   ```

Без токена (пустое значение) бэкенд и фоновая синхронизация продолжают работать:
эндпоинт `/api/sync/tbank` и задача планировщика `sync_tbank` при пустом
`TBANK_TOKEN` просто ничего не делают (не роняются исключением), логируя
предупреждение — остальной функционал (цены, снимки, дашборд) не зависит от
наличия токена.

## Запуск всего стека (`docker compose`)

```bash
docker compose up --build -d
docker compose ps
```

Поднимаются три сервиса:

| Сервис     | Порт на хосте | Порт в контейнере | Назначение |
|------------|---------------|--------------------|------------|
| `db`       | `5433`        | `5432`             | PostgreSQL с данными портфеля |
| `backend`  | `8001`        | `8000`             | FastAPI + REST API + планировщик |
| `frontend` | `3000`        | `80`               | Статика дашборда (nginx) |

> Порты `5433`/`8001` вместо стандартных `5432`/`8000` — на машине разработки эти
> стандартные порты заняты другими проектами. `3000` для фронтенда свободен и
> именно он указан в CORS-настройках бэкенда (`allow_origins`).

При старте сервис `backend` сам накатывает миграции (`alembic upgrade head`)
перед запуском `uvicorn` — отдельно мигрировать базу не нужно.

> **Один раз после новых миграций** (и вообще после любого пополнения базы
> историей) нужно прогнать дозаполнение справочника инструментов:
>
> ```bash
> cd backend && uv run python -m app.instruments.backfill
> ```
>
> Обычная синхронизация приводит в порядок только те инструменты, что
> встретились в операциях её окна (трое суток, `SYNC_OVERLAP_DAYS`). Бумага,
> купленная годы назад и с тех пор просто лежащая в портфеле, в это окно не
> попадает никогда — и признак ограничения в обороте у неё остался бы пустым.
> На портфеле владельца это 251 инструмент, то есть практически весь
> справочник: без прогона «недоступно к продаже» показывало бы ноль.
> Прогон читающий (только списочные методы справочника) и идемпотентный.

Дашборд открывается на `http://localhost:3000`. Собранная статика фронтенда
обращается к бэкенду по адресу браузера (`http://localhost:8001`), а не по имени
сервиса `backend` внутри docker-сети — это код, исполняемый в браузере владельца,
а не внутри контейнера.

## Запуск для разработки (без пересборки образов)

База данных всё равно нужна в контейнере:


Бэкенд с автоперезагрузкой:

```bash

```

Фронтенд с hot reload (Vite dev-сервер на порту 3000 — см. `server.port` в

```bash
cd frontend
pnpm install
pnpm dev
```

## Дизайн-система фронтенда

Интерфейс собирается из готовых частей, а не рисуется заново на каждом экране.
Правило простое: **цвет и размер записаны значением ровно в одном месте**, и
это `frontend/src/design/tokens.ts`.

Источник в TypeScript, а не в CSS, по трём причинам разом: ECharts
настраивается объектом и принимает цвет строкой (классов он не понимает),
достать значение CSS-переменной из JS можно только через `getComputedStyle`,
которого в jsdom нет, а обратное направление — TS → переменные `:root` —
выражается плагином Tailwind в `tailwind.config.js` и проверяется сборкой.
Оттуда же Tailwind берёт утилиты (`text-muted`, `bg-card`, `rounded-lg`,
`text-hero`).

Токены разделены по смыслу: `color` — семантическая палитра, `chart` — оси,
сетка и линия графиков, `assetClass` — цвета классов активов (это про класс
актива, а не про «хорошо или плохо», поэтому к семантике не сводится),
`fontSize`, `radius`.

**Примитивы** — `frontend/src/ui/`:

| Примитив | Для чего |
|---|---|
| `Card`, `CardTitle` | подложка карточки и её подпись |
| `CardState`, `StateMessage` | «загрузка / пусто / ошибка» — три состояния, различимые и цветом, и текстом |
| `Button` | `primary`, `ghost`, `danger`; необратимое действие обязано отличаться видом |
| `Field`, `FieldLabel` | поле ввода с табличными цифрами и связанная с ним подпись |
| `Table`, `Th`, `Td` | таблица; числовые ячейки помечаются `numeric` и получают `tabular-nums` |
| `Badge` | цветная метка статуса |
| `SegmentedControl` | выбор одного из нескольких (под капотом радиогруппа) |

Рядом, в `frontend/src/components/`, живут два компонента о качестве данных:
`AsOfLabel` (возраст котировок и курсов — две даты, а не одна) и
`CoverageNotice` (какой частью портфеля посчитан капитал).

Новый примитив кладётся в `frontend/src/ui/` вместе с тестом рядом; всё, что
знает о доменных сущностях портфеля, — не примитив, ему место в
`components/`.

**Проверка, что дизайн-система не размывается:**

```bash
cd frontend && pnpm check:styles --strict
```

Скрипт считает две вещи и требует нулей: инлайновых `style={{…}}` вне
`ValueChart.tsx` и `AllocationChart.tsx` (там ECharts, и инлайн неизбежен) и
hex-литералов вне `tokens.ts`. Без `--strict` он просто печатает счётчики.

## Тесты

```bash
cd backend && uv run pytest
cd frontend && pnpm exec vitest run
```

Тесты бэкенда поднимают отдельную базу `jarvis_test` на том же Postgres (порт
`5433`) и не обращаются ни к MOEX, ни к T-Invest API: сетевые клиенты в тестах
заменены двойниками/`respx`-моками. Фоновый планировщик тестируется только на
уровне регистрации задач (расписание, часовой пояс, идентификаторы) — сами
задачи в тестах не запускаются.

## Расписание фоновых задач

Планировщик (`backend/app/scheduler.py`, APScheduler) стартует вместе с
FastAPI-приложением (`lifespan` в `backend/app/main.py`) и остаётся внутри
процесса `backend` — отдельного воркера/очереди не требуется. Все четыре задачи
работают по московскому времени (`Europe/Moscow`) независимо от часового пояса
хоста/контейнера (тот живёт в UTC):

| Задача            | Расписание (МСК)                          | Что делает |
|-------------------|--------------------------------------------|------------|
| `refresh_prices`  | пн–пт, 10:00–18:00, каждые 15 минут         | Обновляет последние цены инструментов с MOEX ISS |
| `refresh_fx`      | ежедневно в 12:10                           | Загружает курсы валют ЦБ и курс золота `GLDRUB_TOM` с MOEX |
| `daily_snapshot`  | ежедневно в 19:30                           | Обновляет цены и курсы, сохраняет снимок стоимости портфеля на сегодня |
| `sync_tbank`      | ежедневно в 9:00 и 20:00                    | Синхронизирует операции и позиции со всеми счетами Т-Банка |

`refresh_fx` стоит в 12:10, потому что курсы ЦБ на следующий день публикуются
днём. Отказ ЦБ и отказ MOEX обрабатываются по отдельности: половина курсов
лучше, чем ни одного. `daily_snapshot` перед снимком обновляет и цены, и курсы
сам — снимок важнее свежести любого из источников, и при их отказе он всё
равно будет снят по последним известным значениям.

Сбой при обработке одного инструмента или счёта не останавливает всю задачу и не
роняет планировщик — это гарантируют `refresh_last_prices` и `sync_broker`
(каждый инструмент/счёт обрабатывается независимо, см. их модули). Задача
`sync_tbank` не передаёт синхронизации фиксированную "точку отсчёта": она
вычисляется отдельно для каждого счёта — от его последнего успешного прогона с
запасом на случай задним числом пришедших операций, а для счёта, который ни разу
не синхронизировался, берётся глубокая история. Это то же поведение, что и у
ручного вызова `POST /api/sync/tbank`.

## Курсы, цены и оценка капитала

Совокупный капитал считается в рублях и включает всё: бумаги в любой валюте,
денежные остатки счетов и золото. Складывать доллары с рублями напрямую нельзя,
поэтому каждая величина проходит через курс.

**Откуда берутся курсы.**

- Фиатные валюты — ЦБ РФ, `https://www.cbr.ru/scripts/XML_daily.asp` (см.
  `backend/app/marketdata/cbr.py`). Официальный курс на дату, один источник на
  все валюты портфеля.
- Золото — MOEX, инструмент `GLDRUB_TOM` (`backend/app/marketdata/moex.py`).
  Оно приходит от брокера не позицией по ISIN, а денежным остатком в валюте
  `XAU` — в граммах, — и потому пересчитывается курсом, а не котировкой бумаги.
  В аллокации золото стоит отдельным классом активов, а не в «деньгах»:
  портфель с граммом золота — не портфель с наличными.

Курсы обновляет фоновая задача `refresh_fx` (12:10 МСК, см. таблицу
расписания). Дата курсов отдаётся отдельно от даты котировок (`fx_as_of` рядом
с `as_of` в `/api/portfolio/overview`): котировки обновляются каждые пятнадцать
минут, курсы — раз в сутки, и несвежесть у них разная. `fx_as_of` — самый
старый из курсов, реально участвовавших в пересчёте, а не самый свежий из
имеющихся: золото торгуется на MOEX ежедневно и максимумом по таблице
прикрывало бы курсы ЦБ любой давности, по которым посчитаны доллары и юани.

Валюту, которой курса не нашлось, обзор называет поимённо
(`currencies_without_rate`), и дашборд показывает её в предупреждении. Причина
та же, что и у пары `valued_positions`/`positions_total`: покрытие оценкой
считает одни позиции, и остаток в валюте без курса выпадал из капитала, не
оставив следа ни в одной цифре на экране. Так видно и редкий случай — серебро,
платина и палладий известны разбивке по классам активов, но `METAL_SECIDS`
знает только золото, и курса им взять пока неоткуда.

> **На свежей базе курсов нет до первого прогона этой задачи.** Таблица
> `fx_rate` пуста, и до 12:10 МСК ближайших суток валютная часть капитала не
> считается вовсе: у бумаги есть цена, но перевести её в рубли нечем, и в итог
> не попадают ни валютные бумаги, ни остатки, ни золото. Дашборд об этом
> предупреждает отдельно — красной плашкой «Нет курса к рублю» с перечнем
> валют, не путая её с обычным «нет котировки». Не дожидаться расписания:
>
> ```bash
> cd backend && uv run python -c "from app.scheduler import job_refresh_fx; job_refresh_fx()"
> ```
>
> То же и перед разовыми прогонами (снимок, сверка) на только что поднятом
> стеке.

**Откуда берётся цена.** Основной источник — MOEX ISS. Для бумаг, которых на
MOEX нет (гонконгские, американские), цену отдаёт сам брокер вместе с
портфелем. Источник хранится у каждой цены и виден на экране: в таблице позиций
такая строка помечена как оценка по данным брокера. Это не придирка к
оформлению — оценка по данным брокера не независима, и сверять ею брокера с
самим собой бессмысленно. При равной дате биржа выигрывает у брокера, при
разной — побеждает более свежая цена.

**Недоступное к продаже.** Причин две, и они разные:

- **Заблокированное количество** (`broker_holding.blocked`) — блокировка
  конкретных бумаг на конкретном счёте: залог, незавершённые расчёты,
  исполнительное производство. Недоступна доля позиции, а не вся позиция.
- **Ограничение бумаги в обороте** (`instrument.trading_restricted`) —
  свойство самой бумаги: брокер не даёт ни купить, ни продать. Так выглядят все
  иностранные бумаги портфеля после 2022 года и выпуски, снятые с торгов после
  конвертации. Недоступна позиция целиком.

Обе причины сводятся наружу в одну сумму `restricted_value`. Она **входит** в
совокупный капитал, а не вычитается из него: брокер считает так же, и капитал
обязан с ним сходиться. Отдельная цифра отвечает на другой вопрос — сколько из
этих денег можно потратить сегодня.

Денежные остатки по счетам и валютам отдаются отдельно — `GET
/api/portfolio/cash`; заблокированная часть остатка приходит там же и входит в
`restricted_value` наравне с бумагами.

**Сверка оценки с итогом брокера.**

```bash
cd backend && uv run python -m app.valuation_check
```

Печатает по каждому счёту наш итог рядом с `totalAmountPortfolio` брокера,
расхождение между ними в рублях и в процентах. Инструмент читающий: ходит в API
брокера за итогами и не меняет ничего ни у брокера, ни в базе. Отдельный
модуль, а не тест, потому что сверять есть смысл только на настоящих данных
владельца, а они в тесты не попадают и попадать не должны. Перед прогоном нужно
обновить курсы и котировки — иначе расхождение будет измерять возраст данных, а
не их верность.

Сошедшимся считается расхождение, укладывающееся в оба допуска сразу:
полпроцента от итога счёта и 15 000 ₽ (`TOLERANCE_RATIO` и
`TOLERANCE_ABSOLUTE`). Одного относительного мало: полпроцента от пяти
миллионов — это двадцать пять тысяч рублей, то есть целая позиция, которая
прошла бы как «ок». В допуск укладываются разный порядок округления, разная
секунда котировки и разница между официальным курсом ЦБ и курсом брокера.
Систематические причины расхождения, известные на 10.08.2026, и их вклад в
рублях разобраны в [`docs/roadmap.md`](docs/roadmap.md), раздел «Где мы
сейчас».

### Доходность

    cd backend && uv run python -m app.returns.check

Печатает XIRR и TWR портфеля и разрезов за три периода, прибыль портфеля,
нереализованную прибыль открытых позиций и покрытие данных. Проверяет три
утверждения признака готовности фазы 4a, каждое — вслух и с вердиктом:

- **сходимость XIRR по определению** — потоки портфеля дисконтируются по
  найденной ставке, печатается невязка приведённой стоимости (порог — копейка);
- **точность разложения прибыли** — ценовая часть плюс валютная равны
  нереализованной прибыли по каждой открытой позиции;
- **сходимость разрезов с целым** — сумма по бумагам, деньгам и «Прочему»
  против прибыли портфеля, а расхождение объясняется поимённо: бумаги, у
  которых прибыль посчитать нечем, названы вместе с причиной и своим вкладом.

**Достройка истории стоимости задним числом.** График стоимости показывает
историю с даты первой операции журнала, а не с того дня, когда система начала
снимать снимки. Достройка разделена на два прогона, и разделение не
косметическое: пересчёт приходится повторять — после разбора расхождений, после
починки сопоставления символа, — и если каждый пересчёт заново выгребает сеть,
его перестают делать вовсе.

```bash
# 1. Загрузка исторических котировок и курсов. Ходит в сеть: MOEX по бумагам
#    российских эмитентов, Yahoo Finance по иностранным, ЦБ по валютам, MOEX по
#    золоту. Сотни запросов, минуты работы.
cd backend && uv run python -m app.marketdata.backfill --dry-run   # сначала это
cd backend && uv run python -m app.marketdata.backfill

# 2. Достройка снимков. В сеть не ходит вовсе: считает по журналу, по уже
#    загруженной истории цен и курсов и по сегодняшним остаткам брокера.
cd backend && uv run python -m app.snapshots.backfill
```

`--dry-run` ничего не загружает, а показывает таблицу сопоставлений: какая
бумага куда пойдёт и под каким символом. **Смотреть её до первого прогона
обязательно.** Неверно сопоставленный символ даёт не отказ, а правдоподобную
цену чужой бумаги, и обнаруживается это через месяцы кривым графиком: тикер
`AGRO` на Yahoo принадлежит аргентинской Adecoagro, а `BBBY` после банкротства
2023 года занял бывший Overstock. Часть подмен ловится сама — загрузка
отказывается писать историю, если валюта в ответе Yahoo не совпала с валютой
инструмента, — но совпадение валют не доказывает совпадения компании.

Оба прогона идемпотентны: повторный обновляет уже загруженное, а не двоит.
Достроенная точка помечается в снимке (`source = backfill`) и несёт покрытие
оценкой — сколько позиций удалось оценить из скольких и каких именно не
хватило. Дни с неполной оценкой отмечены на графике треугольником, а не
замазаны: пробел в данных не должен выглядеть как факт.

**Разовая ступенька в графике стоимости** (до фазы 2c). До фазы 2a капитал
считался только по рублёвым бумагам с котировкой MOEX, и ежедневные снимки
писались именно такими — первый снимок после фазы 2a скакнул с 6.94 до
10.93 млн ₽ на портфеле владельца. Достройка эту ступеньку убирает: снимок с
неизвестным покрытием она перебивает, снимок с бо́льшим покрытием — нет.

## Сверка с брокером и расхождения

После каждой синхронизации Джарвис сверяет посчитанные по журналу операций
позиции с фактическим портфелем на стороне Т-Банка (`GET /api/reconciliations`,
баннер расхождений на дашборде). Если по инструменту есть расхождение:

- **Количество не совпадает** — обычно означает, что в истории операций не
  хватает каких-то сделок/корпоративных событий (сплит, погашение, перевод между
  счетами). Проверить историю операций по этому инструменту в приложении
  Т-Банка за период до первой известной Джарвису операции.
- **Есть в журнале, но нет у брокера** / **есть у брокера, но нет в журнале** —
  обычно позиция появилась или исчезла до глубины истории, которую Джарвис успел
  подтянуть (`DEFAULT_HISTORY_DAYS` в `backend/app/sync/service.py`), либо бумага
  выведена/переведена без исполнения операции, которую коннектор умеет
  распознавать.

Расхождения не исправляются автоматически — Джарвис только показывает их, чтобы
владелец мог решить, донастраивать ли глубину истории синхронизации или
разбираться с конкретной бумагой вручную.

## Сертификат T-Bank в `backend/app/connectors/tbank/russian_trusted_ca.pem`

T-Bank (бывший «Тинькофф») выпускает сертификат `*.tinkoff.ru` через цепочку
Минцифры РФ (`Russian Trusted Sub CA` → самоподписанный `Russian Trusted Root
CA`) — после ухода западных удостоверяющих центров это единственная цепочка,
которой подписан домен `invest-public-api.tinkoff.ru`. Этой цепочки нет в
стандартном доверенном наборе Python (`certifi`/Mozilla trust store), поэтому
без явного добавления её TLS-соединение с T-Invest API падает с
`CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain` — не
только в этом окружении, а на любой машине, где эта цепочка не установлена в
системное хранилище отдельно.

Файл `russian_trusted_ca.pem` — это публичные Sub CA и Root CA сертификаты
(секрета в них нет), которые `backend/app/connectors/tbank/client.py`
подключает аддитивно к стандартному набору `certifi` **только для клиента
Т-Банка**: доверие расширяется исключительно в `TBankClient`, на MOEX-клиент
и остальной HTTP-код проекта оно не распространяется.

Проверить, что файл в репозитории соответствует тому, что реально отдаёт
сервер, можно сверкой SHA-256 отпечатков:

```bash
# Отпечатки Sub CA и Root CA из файла в репозитории
openssl crl2pkcs7 -nocrl -certfile backend/app/connectors/tbank/russian_trusted_ca.pem \
  | openssl pkcs7 -print_certs -noout \
  | csplit -s -z -f /tmp/repo_cert -b '%d.pem' - '/-----BEGIN CERTIFICATE-----/' '{*}'
for f in /tmp/repo_cert*.pem; do openssl x509 -in "$f" -noout -fingerprint -sha256 -subject; done

# Отпечатки полной цепочки, которую отдаёт сервер (0 — лист *.tinkoff.ru,
# 1 — Sub CA, 2 — Root CA; сверять со значениями выше нужно 1 и 2)
echo | openssl s_client -connect invest-public-api.tinkoff.ru:443 \
  -servername invest-public-api.tinkoff.ru -showcerts 2>/dev/null > /tmp/live_chain.txt
awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/{print > ("/tmp/live_cert" n ".pem")} /END CERTIFICATE/{n++}' /tmp/live_chain.txt
for f in /tmp/live_cert*.pem; do openssl x509 -in "$f" -noout -fingerprint -sha256 -subject; done
```
