# Джарвис

Агрегатор инвестиционного портфеля: FastAPI-бэкенд + React-фронтенд + PostgreSQL,
с фоновым планировщиком, который сам обновляет котировки, синхронизирует счета
Т-Банка и снимает ежедневный снимок стоимости портфеля — без ручных действий
владельца.

Куда движется проект — [`docs/roadmap.md`](docs/roadmap.md). Описание системы
целиком — [`docs/superpowers/specs/2026-08-07-jarvis-investment-design.md`](docs/superpowers/specs/2026-08-07-jarvis-investment-design.md).

## Требования

- Docker с `docker compose` (Docker Desktop или аналог, например Rancher Desktop) —
  для запуска всего стека одной командой.
- Python 3.12+ с [`uv`](https://docs.astral.sh/uv/) — для запуска бэкенда вне контейнера
  и тестов.
- Node 22.13+ с `pnpm` 11 (через `corepack enable`) — для разработки фронтенда
  вне контейнера. Пакет `pnpm@11` требует именно эту версию Node; более старой
  `node:20-alpine`, как можно было бы ожидать, для сборки фронтенда недостаточно —
  поэтому `frontend/Dockerfile` тоже собирается на `node:24-alpine`.

## Токен T-Invest API

Бэкенд ходит в T-Invest API Т-Банка от имени владельца портфеля, поэтому нужен
персональный токен:

1. В приложении/личном кабинете Т-Банка выпустить токен T-Invest API **с правами
   только на чтение** (без права на торговые операции и вывод средств). Джарвис
   только читает операции, портфель и справочник инструментов — торговый доступ
   ему не нужен и не должен выдаваться.
2. Скопировать `.env.example` в `.env` и вписать токен:

   ```bash
   cp .env.example .env
   ```

   ```
   TBANK_TOKEN=<токен с правами только на чтение>
   ```

Без токена (пустое значение) бэкенд и фоновая синхронизация продолжают работать:
эндпоинт `/api/sync/tbank` и задача планировщика `sync_tbank` при пустом
`TBANK_TOKEN` просто ничего не делают (не роняются исключением), логируя
предупреждение — остальной функционал (цены, снимки, дашборд) не зависит от
наличия токена.

## Запуск всего стека (`docker compose`)

```bash
docker compose up --build -d
docker compose ps
```

Поднимаются три сервиса:

| Сервис     | Порт на хосте | Порт в контейнере | Назначение |
|------------|---------------|--------------------|------------|
| `db`       | `5433`        | `5432`             | PostgreSQL с данными портфеля |
| `backend`  | `8001`        | `8000`             | FastAPI + REST API + планировщик |
| `frontend` | `3000`        | `80`               | Статика дашборда (nginx) |

> Порты `5433`/`8001` вместо стандартных `5432`/`8000` — на машине разработки эти
> стандартные порты заняты другими проектами. `3000` для фронтенда свободен и
> именно он указан в CORS-настройках бэкенда (`allow_origins`).

При старте сервис `backend` сам накатывает миграции (`alembic upgrade head`)
перед запуском `uvicorn` — отдельно мигрировать базу не нужно.

Дашборд открывается на `http://localhost:3000`. Собранная статика фронтенда
обращается к бэкенду по адресу браузера (`http://localhost:8001`), а не по имени
сервиса `backend` внутри docker-сети — это код, исполняемый в браузере владельца,
а не внутри контейнера.

## Запуск для разработки (без пересборки образов)

База данных всё равно нужна в контейнере:

```bash
docker compose up -d db
```

Бэкенд с автоперезагрузкой:

```bash
cd backend
uv run alembic upgrade head   # один раз после новых миграций
uv run uvicorn app.main:app --reload --port 8001
```

Фронтенд с hot reload (Vite dev-сервер, порт по умолчанию 5173, обращается к
бэкенду на `localhost:8001` — см. `frontend/src/api/client.ts`):

```bash
cd frontend
pnpm install
pnpm dev
```

## Тесты

```bash
cd backend && uv run pytest
cd frontend && pnpm vitest run
```

Тесты бэкенда поднимают отдельную базу `jarvis_test` на том же Postgres (порт
`5433`) и не обращаются ни к MOEX, ни к T-Invest API: сетевые клиенты в тестах
заменены двойниками/`respx`-моками. Фоновый планировщик тестируется только на
уровне регистрации задач (расписание, часовой пояс, идентификаторы) — сами
задачи в тестах не запускаются.

## Расписание фоновых задач

Планировщик (`backend/app/scheduler.py`, APScheduler) стартует вместе с
FastAPI-приложением (`lifespan` в `backend/app/main.py`) и остаётся внутри
процесса `backend` — отдельного воркера/очереди не требуется. Все три задачи
работают по московскому времени (`Europe/Moscow`) независимо от часового пояса
хоста/контейнера (тот живёт в UTC):

| Задача            | Расписание (МСК)                          | Что делает |
|-------------------|--------------------------------------------|------------|
| `refresh_prices`  | пн–пт, 10:00–18:00, каждые 15 минут         | Обновляет последние цены инструментов с MOEX ISS |
| `daily_snapshot`  | ежедневно в 19:30                           | Обновляет цены и сохраняет снимок стоимости портфеля на сегодня |
| `sync_tbank`      | ежедневно в 9:00 и 20:00                    | Синхронизирует операции и позиции со всеми счетами Т-Банка |

Сбой при обработке одного инструмента или счёта не останавливает всю задачу и не
роняет планировщик — это гарантируют `refresh_last_prices` и `sync_broker`
(каждый инструмент/счёт обрабатывается независимо, см. их модули). Задача
`sync_tbank` не передаёт синхронизации фиксированную "точку отсчёта": она
вычисляется отдельно для каждого счёта — от его последнего успешного прогона с
запасом на случай задним числом пришедших операций, а для счёта, который ни разу
не синхронизировался, берётся глубокая история. Это то же поведение, что и у
ручного вызова `POST /api/sync/tbank`.

## Сверка с брокером и расхождения

После каждой синхронизации Джарвис сверяет посчитанные по журналу операций
позиции с фактическим портфелем на стороне Т-Банка (`GET /api/reconciliations`,
баннер расхождений на дашборде). Если по инструменту есть расхождение:

- **Количество не совпадает** — обычно означает, что в истории операций не
  хватает каких-то сделок/корпоративных событий (сплит, погашение, перевод между
  счетами). Проверить историю операций по этому инструменту в приложении
  Т-Банка за период до первой известной Джарвису операции.
- **Есть в журнале, но нет у брокера** / **есть у брокера, но нет в журнале** —
  обычно позиция появилась или исчезла до глубины истории, которую Джарвис успел
  подтянуть (`DEFAULT_HISTORY_DAYS` в `backend/app/sync/service.py`), либо бумага
  выведена/переведена без исполнения операции, которую коннектор умеет
  распознавать.

Расхождения не исправляются автоматически — Джарвис только показывает их, чтобы
владелец мог решить, донастраивать ли глубину истории синхронизации или
разбираться с конкретной бумагой вручную.

## Сертификат T-Bank в `backend/app/connectors/tbank/russian_trusted_ca.pem`

T-Bank (бывший «Тинькофф») выпускает сертификат `*.tinkoff.ru` через цепочку
Минцифры РФ (`Russian Trusted Sub CA` → самоподписанный `Russian Trusted Root
CA`) — после ухода западных удостоверяющих центров это единственная цепочка,
которой подписан домен `invest-public-api.tinkoff.ru`. Этой цепочки нет в
стандартном доверенном наборе Python (`certifi`/Mozilla trust store), поэтому
без явного добавления её TLS-соединение с T-Invest API падает с
`CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain` — не
только в этом окружении, а на любой машине, где эта цепочка не установлена в
системное хранилище отдельно.

Файл `russian_trusted_ca.pem` — это публичные Sub CA и Root CA сертификаты
(секрета в них нет), которые `backend/app/connectors/tbank/client.py`
подключает аддитивно к стандартному набору `certifi` **только для клиента
Т-Банка**: доверие расширяется исключительно в `TBankClient`, на MOEX-клиент
и остальной HTTP-код проекта оно не распространяется.

Проверить, что файл в репозитории соответствует тому, что реально отдаёт
сервер, можно сверкой SHA-256 отпечатков:

```bash
# Отпечатки Sub CA и Root CA из файла в репозитории
openssl crl2pkcs7 -nocrl -certfile backend/app/connectors/tbank/russian_trusted_ca.pem \
  | openssl pkcs7 -print_certs -noout \
  | csplit -s -z -f /tmp/repo_cert -b '%d.pem' - '/-----BEGIN CERTIFICATE-----/' '{*}'
for f in /tmp/repo_cert*.pem; do openssl x509 -in "$f" -noout -fingerprint -sha256 -subject; done

# Отпечатки полной цепочки, которую отдаёт сервер (0 — лист *.tinkoff.ru,
# 1 — Sub CA, 2 — Root CA; сверять со значениями выше нужно 1 и 2)
echo | openssl s_client -connect invest-public-api.tinkoff.ru:443 \
  -servername invest-public-api.tinkoff.ru -showcerts 2>/dev/null > /tmp/live_chain.txt
awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/{print > ("/tmp/live_cert" n ".pem")} /END CERTIFICATE/{n++}' /tmp/live_chain.txt
for f in /tmp/live_cert*.pem; do openssl x509 -in "$f" -noout -fingerprint -sha256 -subject; done
```
