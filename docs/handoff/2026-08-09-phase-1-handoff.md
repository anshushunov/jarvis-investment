## Что показал живой прогон 09.08.2026

Дашборд работает, честность работает: под совокупным капиталом стоит оговорка
«цены только для 14 позиций из 61, остальные в эту сумму не входят».

Баннер показывает **32 расхождения, все по счёту «Инвестиционный»**; по счёту «Лежебока»
расхождений ноль — там журнал сходится с брокером в точности, то есть механика считает
верно, когда история полная.

**Разобрано до причины (важно, не повторять диагностику заново).** Взят Сбер
(`RU0009029540`), расхождение «в журнале 1000, у брокера 0»:

- в журнале покупок на 1330 штук и продаж ровно на 1330 — арифметически ноль,
  а материализованная позиция показывает 1000;
- первые операции: **21.02.2022 сначала продажа 1000 по 201 ₽, затем покупка 1000 по 196 ₽**;
- журнал начинается **12.08.2021 — ровно пять лет назад**, потому что
  `DEFAULT_HISTORY_DAYS = 365 * 5` в `backend/app/sync/service.py`;
- проданные в феврале 2022 бумаги были куплены до этой границы, покупки в журнале нет,
  движок не дал позиции уйти в минус и отбросил излишек продажи — это его
  задокументированное поведение при неполной истории (см. `positions/engine.py`).

**Вывод: это не дефект расчёта, а мелкая глубина первой синхронизации.** Сверка
отработала ровно так, как задумывалась. Тем же объясняются и другие группы расхождений:
«у брокера есть, в журнале нет» — бумаги, купленные до августа 2021 и не проданные;
«количество не совпадает» — частично проданные из той же дозаграничной части.

Проверенная и **не** подтвердившаяся гипотеза: переводы бумаг между счетами.
Операция `OPERATION_TYPE_INPUT_SECURITIES` с ненулевым количеством в журнале всего одна.

## Что править в первую очередь

### 1. Глубина первой синхронизации (главное)

Пять лет для этого портфеля мало. Брокер отдаёт дату открытия счёта, и в модели
`Account` уже есть **пустующее поле `opened_at`** (заведено в задаче 3, никогда не заполнялось).
Правильно: при первой синхронизации счёта идти от даты его открытия, а не от
«сегодня минус пять лет». Затрагивает `connectors/tbank/connector.py` (проброс даты
открытия в `BrokerAccount`), `sync/service.py` (`_get_or_create_account`, `resolve_since_for_account`).
Закроет большую часть из 32 расхождений.

После правки понадобится **полная пересинхронизация** счёта «Инвестиционный»:
журнал append-only, старые записи останутся, недостающие допишутся, дедупликация
дубли не пропустит.

### 2. Привести в порядок уже записанные инструменты (действие с данными, не код)

Все 149 инструментов сейчас имеют `kind='share'` и валюту, взятую из платежа первой
операции. Код это уже чинит для новых данных, существующие строки — нет.

```bash
cd backend
uv run python -m app.instruments.backfill    # виды, валюты, названия из справочника брокера (чтение)
docker compose exec db psql -U jarvis -d jarvis -c \
  "DELETE FROM price WHERE source='moex' AND instrument_id IN (SELECT id FROM instrument WHERE currency <> 'RUB')"
# затем обновить цены (эндпоинт/задача планировщика или прямой вызов refresh_last_prices)
```

Пока не сделано: диаграмма классов активов показывает один сектор «Акции»,
покрытие оценкой — 14 позиций из 61.

### 3. Баннер расхождений занимает весь первый экран

Тридцать две строки выталкивают сам портфель ниже сгиба. Свернуть в строку
«Расхождения: 32 — показать» с раскрытием. `frontend/src/components/ReconciliationBanner.tsx`.

### 4. Перевод бумаг между счетами не размаплен

`OPERATION_TYPE_INPUT_SECURITIES` уходит в `OTHER` с отброшенным количеством
(`connectors/tbank/mapper.py`). В журнале такая операция одна, и она даёт вечное расхождение.
Решение нетривиальное: перевод — не покупка, цены у него нет, наивное «считать покупкой по нулю»
испортит среднюю цену и налоговую базу. Честный вариант — отдельный тип, увеличивающий
количество с неизвестной себестоимостью, и явная пометка такой позиции на экране.

### 5. `Overview.positions_value` дословно дублирует `total_value`

`analytics/service.py:181` — два поля с одним значением в контракте API.
Убрать, пока фронтенд не оброс.

## Следующие итерации

- **Мультивалютный пересчёт по курсам.** Сейчас компромисс: рублёвый итог считается
  отдельно, валютные позиции показаны отдельной строкой по каждой валюте. Полноценно —
  источник курсов, их хранение, решение о дате пересчёта. Владелец согласовал этот
  порядок: «вариант 1 для первого прохода, потом вариант 2».
- **Восстановление истории стоимости задним числом.** График наполняется вперёд по одному
  снимку в день. `MoexClient.close_history` написан и покрыт тестами, но не подключён нигде.
  Достроить прошлое по журналу и котировкам — отдельная задача (корпоративные события,
  дни без торгов). Владелец согласовал: «вариант 1, в целевом виде вариант 2 в отдельной задаче».
- **Корректирующие операции.** Если брокер задним числом изменит содержание уже записанной
  операции, она сейчас молча пропускается, и в журнале остаётся старая версия. Журнал
  append-only, правильный ответ — корректирующая запись. Хорошо бы считать такие пропуски
  отдельно от обычных дублей, чтобы они не были невидимы.
- **Остальные три брокера.** Всё необходимое есть: протокол `BrokerConnector`, дедупликация
  без внешних идентификаторов, сверка по счетам.

## Отложенные мелочи фазы 1

Перенесено из журнала хода работ. Часть могла закрыться попутно в волнах правок —
перед тем как чинить, проверить по коду.

- `op_type` хранится как `String(24)`: после чтения из БД это `str`, а не `OperationType`;
  сравнения через `==` и множества безопасны (StrEnum, имя совпадает со значением),
  но `isinstance`/`.name` не работают. Перейти на настоящий Enum-столбец.
- `frozen=True` у `RawOperation` не замораживает вложенный `payload` (словарь мутируем).
  На ключ дедупликации не влияет.
- В построении `PositionState` трижды вызывается `lots.get` вместо локальной переменной;
  докстринг `fold` говорит «sells», хотя приоритет получают все не-INCREASING операции.
- `page.get("items", [])` в клиенте Т-Банка не защищён от `items: null` (паттерн по всему клиенту).
- В сверке дубли ISIN во входном списке брокера молча берут последнюю позицию;
  позиции инструментов без ISIN исключаются без следа.
- Подпись счёта при коллизии имён не включает брокера: два брокера с одинаковым именем
  счёта и одинаковым внешним идентификатором всё ещё схлопнутся.
- Прямые SQL-запросы в обработчиках истории и расхождений вместо сервисного слоя.
- Tailwind установлен и настроен, но вёрстка идёт инлайновыми стилями.
- N+1 при построении подписей счетов в расхождениях (запрос на строку).
- Нет отдельного теста на задачу синхронизации при пустом токене (покрыто косвенно
  через тест эндпоинта); объяснение про UTC/МСК продублировано в README и в коде планировщика.
- `snapshot_by_account` не вызывается из production-кода: разбивка снимка по счетам
  считается и хранится, но наружу не отдаётся.

## Что важно знать про окружение

- **Официальный SDK Т-Банка не существует**: пакет `tinkoff-investments` удалён с PyPI
  вместе со своей зависимостью `tinkoff`, оба upstream-репозитория архивированы.
  Используется свой REST-клиент на httpx поверх `https://invest-public-api.tinkoff.ru/rest`.
- **Сертификат.** `backend/app/connectors/tbank/russian_trusted_ca.pem` — публичные
  Sub CA и Root CA Минцифры. Без них Python не подключается к T-Invest API
  (`CERTIFICATE_VERIFY_FAILED`). Доверие включено только для клиента Т-Банка.
  Проверка отпечатков описана в README.
- **Ограничение частоты.** Справочник инструментов запрашивается пятью списочными вызовами
  на экземпляр коннектора и переиспользуется всеми счетами прогона. Поштучные запросы
  (284 на счёт) приводили к `429`.
- **Токен** — в `.env`, права только на чтение. При пустом токене синхронизация не падает,
  а пишет предупреждение; остальной функционал не зависит от токена.
- Решение о сужении уникальности операции разобрано в
  `docs/decisions/2026-08-08-ledger-external-id-per-account.md`.
