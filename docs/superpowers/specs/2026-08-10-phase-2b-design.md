## 1. Задача

После фазы 2a совокупный капитал считается целиком, но количества бумаг в
журнале расходятся с брокером в двенадцати местах, и все они на счёте
«Инвестиционный». Разница даёт 97 % от расхождения итога с брокером
(−557 843 ₽ из 11 492 050 ₽).

| Статус | Бумага | В журнале | У брокера |
|---|---|---:|---:|
| нет у брокера | iShares Core MSCI Asia ex Japan `HK0000310034` | 79 | 0 |
| нет у брокера | HeadHunter Group `US42207L1061` | 9 | 0 |
| нет у брокера | Kyndryl Holdings `US50155Q1004` | −2 | 0 |
| нет у брокера | NVIDIA `US67066G1040` | −3 | 0 |
| нет у брокера | ТКС Холдинг `US87238U2033` | 40 | 0 |
| нет в журнале | `HK0000051877` | 0 | 79 |
| нет в журнале | `HK0000123577` | 0 | 92 |
| расходится | Meituan `KYG596691041` | 30 | 31 |
| расходится | РусАгро `RU000A0JQUZ6` | 209 | 560 |
| расходится | Т-Технологии `RU000A107UL4` | 408 | 1420 |
| расходится | Корпоративный Центр Икс 5 `RU000A108X38` | 96 | 141 |
| расходится | X5 RetailGroup ГДР `US98387E2054` | 45 | 40 |

Разведка живой базы (10.08.2026) объясняет часть без всяких догадок:

- **РусАгро — не корпоративное действие, а перевод.** Разница ровно 351, и в
  журнале лежит операция `OPERATION_TYPE_INPUT_SECURITIES` от 19.12.2024 на 351
  бумагу. Она попала в `OperationType.OTHER`, а `OTHER` движок позиций не
  считает движением количества. Парного списания нет — бумаги пришли извне.
- **`HK0000310034` 79 → `HK0000051877` 79** — пара с точно равным количеством;
  обе стороны заблокированы у брокера целиком (79 из 79 и 92 из 92 у второй
  гонконгской бумаги).
- **Пары находятся не всегда.** Икс 5 выросло на 45, а излишек ГДР всего 5
  (45 против 40). ТКС Холдинг 40 против роста Т-Технологий на 1012. Kyndryl
  −2 и NVIDIA −3 — отрицательные остатки, следы шортов, а не конвертаций.

Источника сведений о корпоративных действиях у T-Invest API нет, и выдумывать
их система не должна.

### Цель фазы

Каждое расхождение либо исчезает само (потому что система научилась читать
операцию, которую раньше игнорировала), либо имеет зафиксированное решение
владельца с пояснением.

### Границы

**Входит:** переводы бумаг, корпоративные действия, корректирующие записи,
enum-столбец для `op_type`.

**Не входит:** достройка графика стоимости задним числом — она уезжает в
отдельную фазу 2c. Причина: ей нужны сошедшиеся количества на входе, а ещё
исторические курсы валют, которых у нас нет; смешивать её с этой работой
значит утроить фазу.

**Не входит:** перенос себестоимости между своими счетами. `rebuild_positions`
(`backend/app/positions/service.py:26`) сворачивает журнал по одному счёту, и
межсчётный перенос потребовал бы координации свёрток. На живых данных такого
случая нет: единственный ввод бумаг пришёл извне.

## 2. Архитектура

Решения владельца живут в отдельной таблице и **порождают** записи журнала.
Движок позиций по-прежнему читает ровно один вход — журнал.

```
сверка ──► гипотезы (на лету) ──► владелец решает ──► ledger_decision
                                                            │
                                                            ▼
                                              записи в transaction (source='manual')
                                                            │
                                                            ▼
                                            rebuild_positions ──► пересчёт сверки
                                                                  из broker_holding
```

Рассмотренные и отвергнутые варианты:

- **Всё в журнал, решение целиком в `payload`.** Отклонённую гипотезу записать
  нечем: она не порождает движения, пришлось бы класть в append-only журнал
  пустую операцию-заглушку.
- **Слой поправок поверх свёртки, журнал — чистый слепок брокера.** У
  количества появляется два источника истины, и всё, что читает журнал дальше
  (реализованные сделки, налоговая база, достройка графика в 2c), обязано знать
  про второй источник и повторять его правила.

## 3. Модель данных

### 3.1. Новые типы операций

`OperationType` пополняется пятью значениями:

| Значение | Откуда берётся | Что делает с количеством |
|---|---|---|
| `TRANSFER_IN` | `OPERATION_TYPE_INPUT_SECURITIES` от брокера | увеличивает, себестоимость неизвестна |
| `TRANSFER_OUT` | `OPERATION_TYPE_OUTPUT_SECURITIES` от брокера | уменьшает, без реализованного результата |
| `CONVERSION_OUT` | решение владельца | снимает партии в карман конвертации |
| `CONVERSION_IN` | решение владельца | достаёт партии из кармана |
| `ADJUSTMENT` | решение владельца или изменённая операция брокера | открывает или закрывает партии |

Точное написание `OPERATION_TYPE_OUTPUT_SECURITIES` **обязано быть проверено на
живом ответе** перед тем, как попасть в `TYPE_MAP`: в базе владельца такой
операции нет, есть только `INPUT_SECURITIES`. Если написание окажется другим,
операция уйдёт в `OTHER` — молча и незаметно.

### 3.2. Таблица `ledger_decision`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | int PK | |
| `account_id` | FK account | счёт, на котором расхождение |
| `kind` | `conversion` / `adjustment` / `accepted_as_is` | |
| `status` | `confirmed` / `rejected` / `reverted` | |
| `from_instrument_id` | FK instrument, nullable | что списывается |
| `from_quantity` | Numeric(20,8), nullable | |
| `to_instrument_id` | FK instrument, nullable | что зачисляется |
| `to_quantity` | Numeric(20,8), nullable | |
| `cost_basis` | Numeric(20,4), nullable | себестоимость, если владелец её знает |
| `effective_at` | timestamptz | дата события, задаёт владелец |
| `note` | Text, NOT NULL | пояснение владельца, обязательное |
| `proposed` | JSONB | на чём система построила гипотезу |
| `reverts_id` | FK self, nullable | отменяемое решение |
| `created_at` | timestamptz | |

Хранятся только **принятые** решения. Гипотезы в базу не пишутся: они
пересчитываются из сверки при каждом запросе. Повторный показ глушится так —
гипотеза не предлагается, если по этой паре инструментов на этом счёте уже есть
решение со статусом `rejected`.

Ограничения целостности:

- `kind='conversion'` требует все четыре поля `from_*` и `to_*`;
- `kind='adjustment'` требует ровно одну из пар (`from_*` либо `to_*`);
- `kind='accepted_as_is'` требует, чтобы все четыре были пусты;
- `note` непустая при любом `kind`.

Проверяются в домене, а не только CHECK-ограничениями: сообщение об ошибке
должно быть на русском и объяснять, чего не хватает.

### 3.3. Связь решения с журналом

Порождённые записи получают:

- `source='manual'`;
- `external_id` = `decision:{id}:out` или `decision:{id}:in`;
- `payload.decision_id` = идентификатор решения;
- `dedup_key` = SHA-256 от `('manual', decision_id, сторона)`.

`natural_key` (`backend/app/ledger/dedup.py:16`) для этого не годится: он
построен на `RawOperation` и на полях, которых у ручной записи нет.

### 3.4. Признак неизвестной себестоимости

`position` получает колонку `cost_basis_known` (boolean, NOT NULL, default
true). Позиция, в которой есть хоть одна партия неизвестной себестоимости,
помечается, и по ней **не показывается ни средняя цена, ни доходность** — так
же, как 2a поступила с расхождением валют средней цены и котировки.

Это ломающее изменение контракта: `PositionOut.average_price` меняет тип с
`Decimal` на `Decimal | None`, и фронтенд обязан научиться отсутствию значения
до того, как бэкенд начнёт его слать.

### 3.5. Миграции

- `0015` — enum-тип PostgreSQL `operation_type` вместо `String(24)` для
  `transaction.op_type`. Включает все существующие значения плюс пять новых.
- `0016` — таблица `ledger_decision`.
- `0017` — колонка `position.cost_basis_known`.

Откат каждой обязан быть рабочим. У `0015` откат в `String(24)` безопасен;
у `0016` откат удаляет таблицу, и это удаление данных — как `0011` в фазе 2a,
оно должно отказываться, если в журнале есть записи с `source='manual'`,
ссылающиеся на решения.

## 4. Движок позиций

### 4.1. Перенос партий

`OpenLot` получает признак `cost_known: bool`. `LedgerEntry` — поле
`link_id: int | None`, читаемое из `payload.decision_id`; иначе связать две
стороны конвертации не по чему.

- **`CONVERSION_OUT`** снимает партии по FIFO на указанное количество и кладёт
  их в карман под ключом `link_id`. Если открытых партий меньше, чем списывает
  решение, свёртка падает: владелец подтвердил конвертацию количества, которого
  на счёте нет, и молча списать меньше значит тихо разойтись с его решением.
- **`CONVERSION_IN`** достаёт карман и раскладывает партии на новое количество:
  партия `i` переезжает с количеством `qty_i × Q_new / Q_old` и ценой
  `price_i × Q_old / Q_new`, **дата открытия сохраняется**. Суммарная
  себестоимость и пропорции партий не меняются, срок владения не сгорает —
  трёхлетняя льгота выживает.
- **`TRANSFER_IN`** открывает партию с `cost_known=False` и нулевой ценой.
- **`TRANSFER_OUT`** закрывает партии по FIFO **без** `RealizedSale`: вывод
  бумаги не продажа, выручки нет.
- **`ADJUSTMENT`** с положительным количеством открывает партию (себестоимость
  из решения, иначе неизвестна), с отрицательным — закрывает по FIFO без
  реализованного результата.

### 4.2. Порядок обработки

`sort_key` в `fold` сейчас даёт приоритет 0 покупкам и 1 всему остальному.
Расширяется так, чтобы `CONVERSION_OUT` шёл строго раньше `CONVERSION_IN` того
же мгновения — обе стороны решения записываются с одинаковым `effective_at`.

Если `CONVERSION_IN` встретил пустой карман, это порча данных, а не повод молча
открыть партию с нулевой ценой: свёртка обязана упасть с внятным сообщением.

### 4.3. Средняя цена при неизвестной себестоимости

`PositionState` получает `cost_basis_known: bool` — истина, когда известны все
партии. Средняя цена по позиции с неизвестной партией не считается вовсе
(`None`), а не усредняется с нулями: усреднение с нулём даёт правдоподобное, но
неверное число, и владелец примет его за настоящее.

## 5. Гипотезы конвертации

Считаются из строк `reconciliation` по одному счёту:

1. **Излишек в журнале** — `ledger_quantity > broker_quantity`, величина
   `ledger − broker`. Сюда попадают и `missing_at_broker`, и часть
   `quantity_mismatch`.
2. **Недостача в журнале** — `broker_quantity > ledger_quantity`, величина
   `broker − ledger`. Сюда попадают `missing_in_ledger` и остальные
   `quantity_mismatch`.
3. Пара предлагается при **точном** совпадении величин. Отрицательные остатки
   журнала (`ledger_quantity < 0`) в кандидаты на списание не берутся: это
   следы шортов, конвертировать нечего.
4. Если кандидатов с одинаковой величиной несколько, показываются **все**
   варианты с пометкой неоднозначности. Выбирать за владельца система не
   должна — фаза 2a уже показала, чем кончается «правдоподобный» выбор из
   нескольких записей.

**Усиливающий признак** — стопроцентная блокировка у брокера
(`broker_holding.blocked == broker_holding.quantity`). У живой пары
`HK0000310034` → `HK0000051877` это так с обеих сторон. Признак показывается в
карточке гипотезы, но сам по себе гипотезу не создаёт.

Из одиннадцати расхождений, которые останутся после того, как `TRANSFER_IN`
закроет РусАгро, гипотеза найдётся ровно для одной пары — она закроет сразу две
строки. Это не недостаток алгоритма: остальные величины действительно не
совпадают, и подгонять их было бы враньём.

## 6. Изменённые операции брокера

Сейчас конфликт по `uq_transaction_source_external` считается дублем и молча
пропускается (`backend/app/ledger/service.py:24`). Это верно, когда содержание
совпало, и неверно, когда брокер задним числом переписал операцию.

Разделяем два случая. Если тот же `external_id` на том же счёте пришёл с другим
количеством, суммой или ценой — в журнал пишется `ADJUSTMENT`, несущий
**разности** по всем трём величинам сразу (новое минус записанное), с
`payload.corrects_transaction_id`, указывающим на исходную запись. Одна
корректирующая запись на одну изменившуюся операцию, а не по записи на каждое
поле: свёртка обязана увидеть изменение целиком, иначе цена уедет отдельно от
количества. Журнал остаётся append-only, расхождение не пропадает молча.

Частый случай доисполняющейся заявки уже закрыт `STILL_FILLING_WINDOW`
(`backend/app/connectors/tbank/mapper.py:41`), так что этот путь должен
срабатывать редко. Каждое срабатывание пишется в лог: если их вдруг много,
значит обход перестал работать, и это надо заметить.

## 7. Интерфейс и API

Приложение одностраничное, роутера нет; заводить его ради этого не нужно.
Разбор живёт в существующем баннере расхождений
(`frontend/src/components/ReconciliationBanner.tsx`).

Раскрытая строка расхождения получает кнопку «Разобрать» и раскрывающуюся под
ней панель. При наличии гипотезы панель предзаполнена: «79 iShares Core MSCI
Asia ex Japan → 79 `HK0000051877`, обе стороны у брокера заблокированы
целиком». Владелец правит или подтверждает. Без гипотезы панель пустая, с
выбором действия: конвертация, корректировка количества, принять как есть.
Пояснение обязательно во всех трёх случаях.

Инлайновые стили и вёрстка остаются в нынешнем виде — приведение к
дизайн-системе это фаза 3, и смешивать не нужно.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/reconciliations` | существующий; у строки добавляется `suggestion` |
| `GET` | `/api/decisions` | что уже решено — иначе решения невидимы после того, как расхождение исчезло |
| `POST` | `/api/decisions` | записать решение, породить записи журнала, пересобрать позиции и сверку |
| `POST` | `/api/decisions/{id}/revert` | отменить решение контр-записями |

**Отмена решения** не удаляет ни решение, ни порождённые записи. Она создаёт
новое решение с `reverts_id`, порождающее зеркальные записи, и переводит
исходное в `reverted`. Журнал append-only, и это единственный честный способ.

**Пересборка после решения.** Позиции пересобираются из журнала, сверка
пересчитывается **из сохранённого снимка `broker_holding`**, а не походом к
брокеру: снимок лежит в базе с фазы 2a, и подтверждение конвертации не повод
дёргать API и упираться в ограничение частоты запросов. Побочный эффект
полезный: `reconcile_account` перестаёт быть намертво связан с живым ответом
брокера.

## 8. Тестирование

Тесты идут на настоящем PostgreSQL, как и весь бэкенд проекта.

- **Типы операций — только через базу.** Грабля, записанная в роадмепе: тест на
  `LedgerEntry`, собранном в памяти, ничего не доказывает, потому что из базы
  тип приходил строкой. Каждая проверка типа операции покрывается тестом,
  поднимающим данные из PostgreSQL. После перехода на enum правило остаётся в
  силе — оно и проверяет, что переход состоялся.
- **Перенос партий.** 79 бумаг двумя партиями разных дат конвертируются в 79
  новых: суммарная себестоимость и обе даты открытия сохранились.
- **Непропорциональная конвертация.** 40 в 1012: цены пересчитаны, сумма
  сошлась, партий столько же.
- **Пустой карман.** `CONVERSION_IN` без парного `CONVERSION_OUT` роняет
  свёртку, а не открывает партию с нулевой ценой.
- **Неизвестная себестоимость.** Позиция после `TRANSFER_IN` помечена, средняя
  цена и доходность отдаются как `null`.
- **Вывод бумаг.** `TRANSFER_OUT` уменьшает количество и не создаёт
  реализованной сделки.
- **Отмена решения.** Контр-записи возвращают позиции ровно к состоянию до
  решения.
- **Изменённая операция брокера.** Та же операция с другим количеством даёт
  `ADJUSTMENT` на разницу; операция с тем же содержанием по-прежнему тихо
  пропускается.
- **Гипотезы.** Два кандидата с равной величиной дают два варианта с пометкой;
  отклонённая гипотеза не предлагается снова; отрицательный остаток журнала в
  кандидаты не попадает.
- **Миграции.** Откат `0016` при наличии записей с `source='manual'`
  отказывается, а не рушит журнал.
- **Фронтенд.** Компонентных тестов в проекте пока нет вовсе. Панель разбора —
  первый повод их завести, хотя бы на предзаполнение формы гипотезой и на
  обязательность пояснения.

## 9. Признак готовности

- РусАгро исчезает из расхождений **автоматически**, без участия владельца:
  система научилась читать `TRANSFER_IN`.
- Остальные одиннадцать имеют решение владельца — конвертация, корректировка
  или пометка «принято как есть» — и список расхождений после разбора пуст.
- `valuation_check` показывает разницу с брокером меньше 0,2 %: остаётся только
  то, что фаза 2a объяснила курсовой разницей и секундой котировки.
- Позиции с неизвестной себестоимостью честно помечены на экране и не
  показывают выдуманную доходность.

## 10. Что фаза сознательно не делает

- Не угадывает коэффициент конвертации, когда количества не совпадают.
- Не тянет сведения о корпоративных действиях из внешних источников: их нет ни
  у T-Invest API, ни в бесплатном доступе в машиночитаемом виде.
- Не переносит себестоимость между счетами.
- Не трогает вёрстку и дизайн-систему.
- Не достраивает график стоимости задним числом — это фаза 2c.
